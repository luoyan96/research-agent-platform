## 从哪里开始

2026-10-01 已沿用现有 Ubuntu ECS、Nginx、systemd 和 Workbench 完成独立部署。域名/证书、API/worker 常驻、浏览器入口、真实 HTTPS 合成协作、10 MiB 附件、重启和同机隔离恢复通过；模型配置与本人账号仍待完成。[ECS 部署说明](deployment/ecs.md)记录已做与未做的边界，实际网址和账号交接在受控记录中。原本机启动方式保留用于独立演练。

当前选择为现有云实例。原本机演练代理仍只监听 `127.0.0.1`；成员使用新的 HTTPS 域名入口，不能把本机演练地址发给同事。

| 首轮方式 | 需要落地的事项 | 能验证什么 |
| --- | --- | --- |
| 本机先体验 | 独立运行目录、正式个人账号、模型配置、启动/停止与本机入口 | 本人整理任务和使用体验；不能代替多人共同使用 |
| 组内常开电脑或服务器 | 明确局域网/获准访问方式、证书、维护人、浏览器地址与独立账号 | 小组在同一服务上协作 |
| 现有云实例 | 明确可使用的实例、系统、域名/证书、访问范围、维护人与备份位置 | 小组异地访问和持续运行 |

选择某种方式不等于已经提供连接权限或授权开公网。先检查选定环境并形成具体配置，再执行用户已授权的部署动作；不猜主机/账号，不因需要多人访问就直接把所有端口公开。API、worker 和数据库保持受控，成员通过同一 HTTPS 入口使用。

技术操作见 [B5a 联调包](development/b5a-handoff.md)，用户不必逐条学习部署命令。实际主机路径、成员密码、研究内容和备份写入受控运行记录，公开仓库只存通用说明。

## 第一项任务

从用户当前最需要减轻负担的一项工作开始。可以是项目指标核对、申请材料协作或学生工作安排；以前提过的任务与日期需重新核对，不沿用过期承诺。

启动时只需明确：这次要交付什么、谁安排和验收、拟请谁参与、哪些资料可共享、有没有真实截止日期。未知项可以留空，再由协作方案逐步补齐。成员允许使用自己的工具完成工作，不要求贡献私有方法。

一位发起人和一位未参与开发的成员即可开始首项协作。发起人核对方案，成员自己接受并交付，发起人验收；维护者记录哪里需要帮助，不代替成员操作后称其独立完成。首项通过后再选择第二项自然发生的任务，观察是否能复用获准结论。

## 运行交接应给用户什么

- 一个能打开的浏览器地址、受控交付的单次负责人开通码，以及[一页使用说明](first-use.md)。负责人先在网页自行注册，随后从“邀请码管理”签发成员邀请码；成员在网页自行设置独立账号和密码。维护者保留[注册维护入口](deployment/registration.md)用于首次开通及恢复，不代替成员设置密码。邀请码不提交 Git 或公开记录。
- 服务与 worker 的维护人、停止/重启方法、备份位置与恢复点；已验证恢复后再开始放入重要资料。
- 明确 AI 是否已启用、允许传入模型的材料范围及用量上限。新环境先用合成内容检查真实配置，确认后再处理获准资料；手工协作可以先开始。
- 出问题时去哪里报告；真实用户反馈只保留完成判断所需的去敏信息，不收集私人方法和内部日志作为交付条件。
