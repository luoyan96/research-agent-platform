# 科研智能体平台产品规划 v0.2

日期：2026-09-20。状态：用于讨论和试点的产品规划，尚未完成真实需求验证。实现状态见[README](../README.md)，验证方法见[试点验证计划](validation-plan.md)，开发顺序见[路线图](roadmap.md)。

## 1. 我们要做什么

**面向科研人员，做一个可以找到、使用和共享科研智能体的平台；让一次工作中积累的资料、成果和确认过的知识，能够支持下一次工作。**

长期服务两类人：需要完成科研任务的使用者，以及能够提供有效科研能力的作者。起步时双方都来自自己的小组，可以由同一人兼任；随后检验未参与搭建的成员、其他课题组和外部作者能否加入。

用户通过统一的浏览器入口使用平台，任务由常开服务管理。DeepSeek Harness 是拟采用的运行底座，插件和 Skills 是能力的实现方式。普通使用者获得的是完整的产品体验，无需自己管理这些组件。

本规划采用讨论中“第二阶段”的工作定义：任务型智能体逐步丰富，平台帮助供需双方相遇，并降低选择、使用、复用和维护能力的成本。第一版由人选择能力、授权资料和判断结果；跨智能体自主规划、自动组织整个科研过程属于更后续的探索。这里是我们的产品解释与选择，不作为作者原文引用或市场已经成立的结论。

### 决策状态

| 状态 | 内容 |
|---|---|
| 已确定 | 从科研场景与自己的小组开始；统一浏览器入口；后台任务；可管理的记忆与知识留存；共建能力并逐步向外验证；以 Harness 为拟定底座 |
| 本版提出的试点建议 | 先用一条“整理依据→形成材料→人工检查”的工作链，验证两项可独立使用的能力；具体材料类型仍需选定 |
| 尚待验证 | 哪项任务值得反复使用；平台比现有做法多大程度上更省事；非作者能否独立使用；外部作者是否愿意维护；谁愿意付费 |

## 2. 为什么值得尝试

发起人已经说明自己的工作包括论文、项目申请、各类材料和实习生安排。这证明我们有接触真实工作与持续试用的条件，尚不能证明其他研究者也有同样的困难，或愿意迁移到新平台。

以下是需要观察的需求假设，不是已经完成的访谈结论。

| 需求假设 | 用户希望获得的变化 | 平台需要提供的增量 | 如何证伪或验证 |
|---|---|---|---|
| N1：重复解释背景、寻找旧材料占用精力 | 下次任务可以接着已有工作做 | 项目上下文、成果与已确认记忆的持续复用 | 比较两次同类任务的准备时间，以及取错、漏取背景造成的返工 |
| N2：知道有很多工具，却难以判断哪个适用、怎样运行 | 按手头任务选到能用的能力 | 明确的适用范围、输入输出、示例、可用状态和统一运行入口 | 观察非作者能否完成选择与首次使用；记录求助、误选和放弃 |
| N3：一个人的有效方法很难交给别人重复使用 | 同伴能直接使用并反馈 | 可运行的能力版本、发布说明、实例和结果反馈 | 作者不在旁指导时，另一人能否完成任务；后续是否仍需逐次定制 |
| N4：成果与决策分散，换人或换会话后难以继续 | 找到当前版本、判断依据并接手 | 任务、资料、成果、记忆之间的明确关联 | 让有权限的另一位成员继续工作，观察需要补问什么、重复做什么 |

现有聊天产品、个人 Skills、文档与团队协作工具也能覆盖部分需求。试点要与参与者实际正在使用的组合比较，记录输入准备、执行、检查、返工和交接的完整成本。若通用 AI 加共享文档已能更简单地完成工作，应据此缩小或调整平台范围。

## 3. 首批服务谁

首批核心使用者是正在承担具体科研产出的研究者，例如需要准备材料、检查依据和接续项目工作的博后或研究生。研究方向暂不限定，任务的输入与验收标准必须具体。

| 角色 | 核心职责与诉求 |
|---|---|
| 任务使用者 | 提供目标与材料、选择能力、处理必要判断、检查并采用成果 |
| 能力作者 | 将一种已经有效的方法做成别人能运行的能力，维护版本并处理反馈 |
| 项目负责人 | 确定共享范围、重要项目背景与决策，帮助成员衔接工作 |
| 平台维护者 | 保证已发布能力的可用状态清楚，处理运行问题、版本和使用成本 |

试点应包含未参与开发的成员；核心团队熟悉内部约定，可能掩盖普通用户的使用困难。实习生安排和进展汇总属于候选需求，首版暂不扩展为完整的人事、培养或实验室管理系统。

一个“项目”是围绕一项持续科研工作的资料与任务空间，可以由个人使用或邀请同伴。它可以对应论文、申请书或其他工作，不专指科研经费项目。每个任务有使用者，每份待检查成果有明确检查人；有工具参与不改变人的科研判断责任。

## 4. 平台价值怎样形成

```mermaid
flowchart LR
    A[作者将有效方法做成可运行能力] --> B[研究者按任务选择]
    B --> C[带着授权的项目背景执行]
    C --> D[人工检查与采用成果]
    D --> E[留下使用反馈]
    E --> A
    D --> F[留存成果与确认过的知识]
    F --> C
```

这里有两件需要分别成立的事：同一个人下一次使用时更省事；另一个人能够使用作者提供的能力。只有前者成立时，证明的是个人或团队工作空间的价值。还需要后者及持续的供需参与，才能支持进一步的平台判断。

初期供给由组内成员整理自己的方法，也可以适配已有开放能力。网上找到的 Skill 或智能体先作为候选，经过输入输出、工具依赖和真实任务验证后，才作为平台上可运行的能力提供。十项已有 Skills 是候选资产，不预设必须做成十个首发智能体。

| 名称 | 本产品中的含义 |
|---|---|
| Skill | 做事方法及配套资源，可以被不同智能体复用 |
| 智能体条目 | 可运行的任务能力，组合输入输出要求、模型与工具、Skills、访问范围、作者和版本 |
| Harness 插件 | 接入执行环境的技术扩展单元，可以支撑一项或多项能力 |
| 平台 | 为使用者与作者提供选择、运行、资料留存、发布和反馈的整体产品 |

用户进入平台是为了完成手头工作。第一版按任务类别、适用范围和示例帮助选择；没有合适能力时明确显示缺口，允许留下需求。需求记录用于决定下一项能力，不伪装为已有能力。供给规模扩大后，再验证推荐、排序和更复杂的匹配方式。

作者最初可能从自己的工作提效、同伴复用与共同维护中受益。外部作者的动机、支持成本、归属署名以及商业回报需要单独验证；内部贡献热情不能替代外部供给证据。

## 5. 建议用什么任务起步

**建议先试同一真实工作链中的两项能力：资料与依据整理，以及基于已选依据的材料草稿或修改。** 二者可以分别使用，由人检查后衔接。这个建议来自发起人已说明的工作范围，尚不是已确认的首发需求。

| 能力候选 | 输入 | 交付物 | 本次不承诺 |
|---|---|---|---|
| A：项目资料与依据整理 | 用户提供的一组可读取材料、明确问题、允许使用的项目背景 | 带原文定位的依据清单、相互矛盾处、缺失信息和待确认问题 | 自动找到所有相关文献，或把没有来源的推断当成事实 |
| B：材料草稿与修改 | 用户选定的依据、受众、模板或段落要求、已有版本 | 符合本次要求的草稿或修改稿、所用依据与待人工补充项 | 一次生成可直接提交的完整论文或申请书 |

选择这条链是为了同时观察资料留存、两种能力的选择与复用、人工检查和成员交接。真正验收对象是研究者所需的那份材料；两个能力都运行过，不等于任务已完成。

M0 先选定一种具体材料，例如一份申请书中的限定段落或某类工作材料。用少量真实输入约定什么结果算可用，再决定是否采用上述候选。资料解析范围随这一样本明确；不能在“支持科研文档”这个笼统表述下默认支持所有格式。

如果近期最频繁、最难解决的实际任务是实习生交接或进展汇总，可以用证据替换候选场景。选择依据是近期会发生、资料可取得、结果可判断、存在非作者复用机会，而不是哪类演示最容易做。记录模板见[试点验证计划](validation-plan.md)。

## 6. 使用者完整过程

1. **进入工作空间。** 新建或选择项目，看到目标、资料、当前成果与待处理任务；首次使用只补齐本次任务需要的背景。
2. **选到适用能力。** 按手头任务查看能力说明、必要输入、输出示例、维护者、版本、局限与最近验证范围。示例不能表示本次一定成功。
3. **提交可执行任务。** 说明目标和完成标准，选择允许使用的资料与记忆，确认本次用量上限。关键输入不全时先补齐；没有实测依据时不展示虚构的耗时和费用预测。
4. **离开后也能继续。** 关闭页面不取消已接收任务；回来时查看真实进度、待补充信息或异常。可以取消尚在进行的任务，看到已经产生的结果与用量。
5. **处理人的判断。** 智能体遇到缺少依据、方向分歧或需要授权的操作时，保存进度并提出具体问题。使用者回复后继续；无法继续时明确结束原因与已有输出。
6. **检查交付。** 使用者对照完成标准和来源，标记采用、需要修改或不采用。需要修改时保留上一版与修改理由；生成的交付物先标为待检查，技术执行完成不能自动表示成果已被采用。
7. **为下次留下积累。** 成果自动关联项目、任务和能力版本；需要长期沿用的新判断作为候选记忆，由有权限的人确认。另一成员在同一权限范围内接手时能找到这些依据。
8. **反馈能力问题。** 选择输入不清、结果错误、运行失败等原因并补充说明。向作者分享具体材料时由使用者明确选择范围。

如果没有合适能力、材料解析失败、依赖不可用、预算耗尽或任务中断，用户应看到原因、已保存内容和下一步选项。可以补充、重试或转为人工处理；这些情况要计入试点记录，不能只统计成功样例。

## 7. 作者完整过程

1. 提交一种任务能力：适合谁、解决什么、所需输入、预期输出、工具与 Skills、限制、维护者和示例。
2. 用可公开或合成样例试运行。维护者检查是否真正可运行、输出能否核对、资料范围是否明确，并邀请一位非作者使用待发布版本，记录试用结果。
3. 发布固定版本，显示验证范围与当前可用状态。第一版允许作者提交配置、由维护者代为发布；无需先开发可视化编排器。
4. 查看被授权共享的反馈、失败类别、结果采用情况和支持投入。默认反馈不包含用户完整研究资料或全部对话。
5. 根据问题修改并重新验证，发布新版本。旧任务仍关联原版本与当时材料，不能随升级改写历史。
6. 能力暂时不可用时停用并说明原因，阻止新任务继续误用；受影响的已有任务需要给使用者明确处理选项。

共享一项方法不等于共享该方法曾经处理的科研数据。可发布内容与项目私有材料分开；第一版由维护者审核接入，外部任意代码的自由安装后置。

## 8. 最小版本的产品需求

P0 是组内最小版本必须形成的完整过程；这些能力应围绕首批任务实现。P1 在 P0 试用后按证据增加，不能因列入规划就一起开工。下表是验收要求，当前均不代表完整平台功能已实现。

| 编号 / 关联需求 | P0 要求 | 可观察的验收 |
|---|---|---|
| R1 / N1、N4 | 成员身份、单人或共享项目、明确的成员访问范围 | 非作者能加入授权项目并继续已有工作；无权成员通过页面、接口和智能体工具均不能读取该项目 |
| R2 / N2、N3 | 小型能力库、任务分类、输入输出示例、维护者、版本与可用状态 | 非作者仅凭说明能够选用能力；不适用或未接通的能力不会被表示为可运行 |
| R3 / N1、N2 | 后台任务、保存状态、等待输入、取消、失败说明、有限重试与用量上限 | 关闭页面后任务仍受管理；重新进入原任务不会再创建一份；中断可见，有明确的恢复或重跑方式 |
| R4 / N1、N4 | 资料、成果和来源留存；支持试点选定的格式；检查与修订 | 从一份成果找到输入资料、来源位置、任务和能力版本；能区分待检查、已采用、需修改和未采用；另一个人能接手 |
| R5 / N1、N4 | 可查看、确认、修改、删除或停用的项目记忆；任务前可选择使用范围 | 新会话能使用确认过的信息；更新的决定生效，过期信息不作为当前依据；未授权项目不会被取用 |
| R6 / N2、N3 | 作者提交、维护者验证发布、版本更新、停用与反馈 | 作者提供的能力被另一人独立使用；一次实际反馈能回到作者并形成可追溯的处理结果 |
| R7 / N1、N4 | 资料与成果导出、成员退出后的访问收回、内容移除规则 | 用户能带走自己有权导出的原文与成果；撤回访问后新任务不能再获取资料，受影响的进行中任务被停止或重新授权；移除内容不再供后续任务检索 |

P0 的记忆先从本次任务相关的项目目标、约束和确认决策开始。个人长期偏好、一次性定时与周期任务、更丰富的检索、能力比较和通知渠道列为 P1。原 v0.1 将个人记忆与定时任务也放入首版；本次拆开优先级，以先验证持续工作与跨成员复用。若选定的首批任务本身依赖定时触发，就将所需的最小定时能力提升为 P0，并同步验收无人在线触发。

“持续运行”在 P0 中表示任务不依赖浏览器保持打开，工作状态与成果可以跨会话保留；不表示模型持续空转或所有任务在崩溃后自动无损续跑。服务器重启后，待执行任务可继续领取；进行中的任务标记中断，根据可靠记录恢复或明确重跑，已发生的外部操作需要避免重复。

建议入口是工作首页、项目、任务和能力库。首页围绕进行中的工作与待检查事项；项目集中资料、成果和记忆。页面形态服从上述流程，当前不先确定复杂导航和视觉稿。

## 9. 什么可以积累，怎样继续使用

| 对象 | 保存什么 | 后续使用规则 |
|---|---|---|
| 任务记录 | 目标、授权输入、执行尝试、工具结果、待处理事项、用量 | 为恢复、检查和接手提供依据；历史日志不自动变成长期事实 |
| 原始资料与成果 | 原文、来源、时间、版本、检查状态、与任务的关系 | 原文是核对依据，摘要和索引可以重建；被移除的内容不继续作为可用资料 |
| 项目记忆 | 目标、约束、确认过的决定及原因、未解决问题 | 记录来源、归属、确认人、更新时间，以及候选／已确认／已替代状态 |
| 个人记忆（P1） | 使用者自己维护的偏好与长期信息 | 默认本人可见；共享范围明确，允许修正和删除 |
| 可复用方法 | Skills、执行配置、示例、验证结果和版本 | 作为能力发布，由作者维护，不把私有研究内容混进公共方法 |

每次任务只获取成员有权使用且与本次目标相关的信息。候选判断、未采用结果和相互矛盾的材料保留各自状态；出现冲突时让人判断，不能静默合并成“事实”。重要来源与成果之间需要能核对。

本阶段的积累依靠资料管理、检索和明确的确认流程，不预设训练模型，也不承诺系统自动从所有聊天中学会正确知识。删除规则应说明停止检索、原文移除与备份留存的区别；具体期限在试用前明确，不能仅隐藏页面却继续提供给任务。

## 10. 怎样判断产品成立

**核心观察是：非作者能否完成并采用结果，下一次真实出现同类需求时是否主动复用，作者是否能够以可承受的维护投入继续提供能力。**

| 观察项 | 记录口径 |
|---|---|
| 独立完成与采用 | 从所有真实尝试中，分别记录技术完成、成果采用、作者协助和放弃；不能用进程成功率替代任务成功率 |
| 实际收益 | 与原有工作方式比较准备、检查、返工、交接的人工时间；另记等待时间、模型与服务成本、作者支持和维护投入 |
| 重复使用 | 在下一次有同类需求的机会中观察是否再次使用及原因；没有新任务的人不算流失，不以每日登录为目标 |
| 能力复用 | 看非作者、不同项目和后续不同课题组的采用情况，以及每次是否仍需作者大量改写 |
| 知识复用质量 | 记录正确取用、过期误用、缺失和需要补充的背景；权限错误单独处理 |
| 作者反馈循环 | 真实反馈是否导致改进，改进后的能力是否再次被别人采用，作者是否愿意持续负责 |

组内试点的样本用于发现问题，不用于宣称市场规模或统计显著性。具体记录表、比较方式和继续／调整条件见[试点验证计划](validation-plan.md)。

如果只能靠作者陪着使用，先改进说明、输入要求或能力本身。如果节省的生成时间被检查和返工抵消，先修正任务范围与质量。如果用户只需要一个固定工具，或只有我们愿意贡献能力，就重新判断哪些平台投入值得继续，避免用增加目录条目代替证据。

## 11. 推进顺序与组织方式

| 阶段 | 要回答的问题 | 阶段产出与通过依据 |
|---|---|---|
| M0：选定真实需求 | 哪份具体工作值得优先解决，什么叫做好？ | 实际工作样本、原有做法、结果标准、首批参与者；决定采用或替换候选工作链 |
| M1：完成最小平台过程 | 能否选择、执行、检查、留存，并由另一个人继续？ | 围绕同一真实工作实现 R1–R7；同时验证后台任务、重启中断与项目权限等必要工程条件 |
| M2：证明非作者重复使用 | 离开开发者指导，是否仍然有效且值得再来？ | 独立使用与下一次需求记录、实际收益、失败与放弃原因、至少一次反馈改进后的再次使用 |
| M3：验证跨组供需 | 平台能否在相似任务上服务新的用户与作者？ | 其他课题组能够复用；外部作者按共同规则贡献；记录引入与维护成本，单独检验付费意愿 |

每个阶段根据证据决定继续、缩小或更换场景，暂不承诺开发周数。组内成功后先沿相似任务和合作关系扩展；进入整个实验室、学校或其他学校需要再次验证。面向个人自然增长与学校采购是不同路径，商业模式仍待明确。

团队共建 Git 仓库，按可检查的结果分工：产品与科研质量、平台执行、科研能力、用户试用。一个人可以兼任，但每项工作有负责人、结果与检查方式；AI 原生的协作方式不能替代这些责任。代码、方法和可公开评测共同版本化，私人科研资料与运行记忆由平台管理。

## 12. 当前不做，以及下一步要补的事实

公开市场与支付分成、全校统一身份与采购、大型实验室管理、任意第三方代码安装、跨智能体自主组织科研、模型训练和完整论文编辑器，均在出现对应需求与证据后再评估。

在投入完整产品开发前，优先补齐三件事：

1. **一个近期实际会发生的工作样本**：到底是哪份材料或任务，当前怎样做，卡在哪里，什么结果可以采用。
2. **最初的使用者与作者**：谁提供方法、谁独立使用、谁判断质量，以及谁愿意负责下一次修改。
3. **采用范围和使用边界**：需要哪些输入、允许哪些人访问、哪些操作和结果必须由人决定。

这些是当前规划明确保留的需求缺口，不能由选择框架、服务器或增加功能清单来替代。[试点验证计划](validation-plan.md)提供记录方法；技术实现与历史盘点另见[架构说明](architecture.md)、[工程依据](engineering-baseline.md)和[迁移记录](migration.md)。
