# 任务分配与能力边界

日期：2026-09-21。对应[产品规划 v0.3](product-plan.md)。状态：待实现的行为设计与验收规格，不是已运行服务。当前代码仅有本地 Project / Artifact 基础和 Skills 加载，尚无成员认证、匹配服务、任务分配或持久化执行系统。

## 1. 核心约定

用户从一个对话入口提出需求，确认一份协作方案后，后台才产生有效任务安排。参与者对约定的交付负责，可以用自己的私有方法完成，不必向发起人公开私有智能体或过程。

任务分配系统管理结果、承诺、依赖、状态与交接。智能体运行系统负责实际执行。AI 可以建议安排，但不能用生成的文本替代真实状态，也不能自行假定某人接受任务。

## 2. 两层匹配

| 层次 | 可用于匹配的信息 | 输出 |
|---|---|---|
| 为共同任务组织协作 | 本任务有权读取的背景、公共能力及可用状态、成员主动公开的专长与可投入时间、允许共享的任务承诺 | 公共智能体执行建议、候选协作者、开放认领项、缺口与推荐理由 |
| 参与者决定怎样交付 | 本人有权读取的任务资料、本人私有能力、公共能力 | 本人的执行方案；私有方法留在本人范围，只提交已选择共享的成果 |

不能先读取所有人的私有能力，再把结果过滤成“看似公开”的推荐。私人名称、能力 ID、配置、提示词、运行日志、工具凭据及由这些内容生成的理由均不得进入其他成员的匹配上下文。公共能力缺失时，不得透露“某人私下有这个能力”。

个人无需上传其能力，也可使用平台外工具完成任务。平台只知道其自愿公开的任务能力、承诺和交付。公共任务中不要求填写私人方法标识。

发起人也可以为自己承担的部分匹配自己的私有能力。个人方案与共同协作方案需要分别按读取者生成：发起人不能看到承接者的私人方法，承接者也不能因参与任务而看到发起人的私人方法。不能把包含个人方法的整份规划上下文直接复制为共同任务说明。

## 3. 方案确认

方案包含版本、发起人、目标、候选任务、交付与验收标准、拟分配方式、候选人员或公共能力、时间建议、依赖、数据范围和必要用量限制。

- 确认前只有草案，不邀请他人、不占用成员承诺、不启动有实际成本的执行。
- 确认作用于明确版本；版本已改变时展示差异，避免确认过时安排。
- 同一确认请求重试只产生一组任务。方案确认与任务写入应在持久化存储中原子完成；外部邀请或执行通过可重试、去重的待办事件派发。
- 后续修改沿用任务身份并记录变化，不能删除旧承诺后重新建一套伪装成从未执行的任务。
- 如果选择开放认领，确认页面说明对谁可见。任务材料只展示认领所需摘要；受限材料在有权承接后才开放。

## 4. 四种分配方式

| 方式 | 生效条件 | 后续行为 |
|---|---|---|
| 本人承担 | 发起人明确选择由自己牵头 | 保留交付与节点，可自行使用公共或个人能力 |
| 指定邀请 | 发起人确认拟邀请对象及任务范围，受邀者接受 | 接受前为待承接，不算已承诺的工作；可以拒绝、提出条件或建议别人 |
| 开放认领 | 任务允许认领且成员具备访问与承接资格 | 牵头者认领成功后形成承诺；多人协作通过明确参与名额或协作申请追加 |
| 公共智能体执行 | 公共能力可用、任务数据授权有效、依赖满足且用量约束允许 | 进入执行队列；保留人类责任人和验收人；运行失败不能显示任务已完成 |

私人智能体不会作为可供其他成员调用的分配目标。人承接之后使用何种个人工具，是个人执行方式。

公共能力由有权发布的所有者或维护者明确发布，并确认可使用范围。个人能力不会因在共同任务中使用而自动变为公共。停止共享时阻止新的公共调用，向已受影响的任务提供处理选项；不能宣称可以从他人已取得的副本中自动撤回先前明确共享的内容。

个人能力转为公共能力必须得到所有者明确授权。任务发起人或公共能力维护者的角色本身不授予代替个人决定公开的方法权限。

每个可执行任务有明确牵头责任；可以有多个协作者。公共智能体承担执行时，人类责任人处理方向、授权、异常和验收安排，不能用智能体名称代替责任归属。

## 5. 任务记录与共享范围

| 记录 | 内容 | 读取范围 |
|---|---|---|
| 共同任务 | 目标、交付要求、验收标准、发起人、牵头者、参与者、验收人、状态、依赖、时间与方案版本 | 有权参与或管理该任务的人；认领前仅必要摘要 |
| 分配与承诺 | 邀请、接受、拒绝、认领、退出、转交与变更记录 | 相关人员及有权组织本任务的人 |
| 公共能力调用 | 公共能力版本、授权输入、实际运行状态和用量 | 按任务范围；公共能力维护者不自动获得任务材料 |
| 交付记录 | 成果版本、必要来源、提交说明、验收或修改意见 | 任务约定的共享范围 |
| 个人执行记录 | 个人能力、私人提示词、内部工具与执行方法、私人反馈 | 所有者及其明确授权者；不放进共同任务字段或事件 |

共同任务中关于“由成员完成”的记录，不应附带自动填充的私人能力 ID。成员如果主动在交付物中选择披露方法，按其明示范围处理，不推定可再次发布到公共能力库。

## 6. 生命周期

任务状态与智能体运行状态分别维护。一次运行结束，只可能带来待检查的交付，不自动代表任务完成。

| 状态 | 含义与退出条件 |
|---|---|
| 待安排 | 尚无明确执行安排；补齐方案后邀请、开放认领或选择本人/公共智能体 |
| 待承接 | 等待受邀成员接受，或等待认领；无承诺前不能表示有人正在处理 |
| 待开始 | 人已接受或公共执行配置已确认；等待前置条件与实际开始 |
| 进行中 | 承接者已开始，或智能体执行服务已确认运行；仅被推荐不进入该状态 |
| 受阻 | 缺少材料、判断、有效授权或其他依赖；记录阻碍与希望谁采取什么动作 |
| 待验收 | 提交了明确版本的成果，等待指定验收人处理 |
| 需修改 | 验收人说明差距，承接者可以修改并再次提交，或协商调整任务 |
| 已完成 | 验收通过，或探索型任务达到事先约定的证据与总结要求 |
| 已取消 | 停止后续安排，保留已发生的承诺、操作与成果；取消不等于外部操作已经撤销 |

技术运行另记排队、运行、等待输入、失败、中断、取消和结束。失败或中断要反映到任务的待处理情况；不能用模型一句“已完成”覆盖运行记录或验收决定。

人类任务可以在平台外完成，通过提交结果接续，无需强制记录每一步私人操作。

## 7. 时间、投入与依赖

- 硬性截止由用户提供或从授权资料中取得并确认；建议日期、成员承诺日期和检查点分别标明。没有依据时允许未知，不生成虚假承诺。
- 人工预计投入、机器运行耗时和预算分别表达。成员可修改自己的投入估计，不按任务数量推断负荷。
- 邀请尚未接受的投入与已接受承诺分开显示。承接时提示已知冲突，由当事人接受或调整；不将推荐自动升级为强制排班。
- 成员的私人任务详情不公开。需要匹配空闲程度时，使用其自愿共享的可投入时间或粗粒度忙闲信息。
- 任务依赖必须无环，不依赖自己；执行前检查前置交付是否可用。上游被取消、验收退回或关键成果更新时，明确提示下游影响，不能默默继续使用失效依据。
- 探索任务用问题、待检验假设、投入上限和检查点表达；获得负面结果可以是有效交付，不能强制每项探索得到预设结论。

## 8. 变更、争用与恢复

| 情况 | 规则 |
|---|---|
| 两人同时认领牵头位置 | 以事务或版本条件保证只有一人成功；另一人收到实际结果，可申请协作；不产生两个互相矛盾的承诺 |
| 重复点击确认、接受或提交 | 使用稳定请求标识去重，返回原结果，不重复创建任务或交付版本 |
| 受邀者拒绝 | 保留拒绝事实与愿意共享的说明，任务回到可安排状态；不擅自再指派给别人 |
| 承接者退出或需要转交 | 保留已有成果，明确未交付部分；重新安排；原承诺不能假装已由下一人接受 |
| 改目标、截止或交付范围 | 展示变化与影响，受影响的成员重新确认承诺；默认延续原约定直到变更被接受或原任务明确取消 |
| 任务取消或权限撤回 | 停止新的访问与执行，处理排队和运行中的工作；已经发生的外部操作保留记录，必要时人工处理 |
| 公共能力停用或失败 | 不再启动新调用；提示受影响任务，提供重试、替换能力或邀请成员等建议，由有权人员决定 |
| 服务中断或重启 | 持久化恢复已确认任务与承诺；未完成的外部派发去重重试；运行中断显式呈现，不宣称任意脚本可以无损续跑 |

重要变更在受影响任务的上下文中处理，不要求用户另外找一个管理页面。常规自动推进仅发生在已确认的目标、访问范围和执行约束内。

## 9. 权限与反馈

任务发起人可组织任务、提出分配与变更，并在自身授权范围内查看共同进度；承接者可接受或拒绝、开始、报告受阻、提交结果和申请退出；验收人可通过或说明修改要求。组织身份不自动授予他人的私人能力权限。

私有性检查贯穿匹配、接口、工具、搜索、日志、导出和反馈，而不只是页面可见性。私人执行错误只向所有者提供内部细节，对共同任务报告影响和需要采取的动作，不能泄露私人配置。

默认保留共同任务的交付与验收反馈。是否用某份成果改进公共能力，另看授权范围；不能自动抽取成员私有过程、私人修订或私人反馈。公共能力维护者看到的内容应是被允许共享的反馈或经过确认的样例。

应用中的访问控制不等于对服务器运维人员的加密隔离。个人能力在共享服务器、独立个人服务或本地运行的取舍，应按实际保密要求决定；在实施与验证前不宣称“管理员也无法读取”。

## 10. 首版验收场景

以下均待实现与测试。本文件描述产品预期，不代表测试已通过。

1. 发起人确认一份含本人、公共智能体和受邀成员的方案；受邀者拒绝时任务保持可重新安排，其他已确认部分正常推进。
2. 成员用未登记或私有的方法交付，任务正常验收；发起人、公共能力作者及无关成员无法从方案、推荐理由、日志或导出取得私人方法。
3. 私有能力所有者能在自己的执行环境使用它；同一能力不出现在他人的目录、搜索、匹配上下文和缺口解释中。
4. 两位成员同时认领同一牵头任务，仅一人成功；协作者加入另有明确记录。
5. 同一方案确认因网络重试提交多次，只创建一组任务；服务重启后仍保留已接受的承诺和未处理事项。
6. 下游依赖未通过验收时不自动执行；上游受阻、取消或更新会给出实际影响。
7. 成员已经接受后，系统建议提前截止或扩大交付范围，变更不会静默覆盖原承诺。
8. 智能体运行结束但结果被要求修改，任务不能显示已完成；人的外部交付不因缺少私人执行日志而被拒收。
9. 公共能力使用被授权的反馈发布新版本，个人能力的配置、内部记录和反馈仍保持私有。
10. 无权成员直接调用接口或工具、查看错误详情、导出任务或检索材料时，仍无法绕过访问范围；权限撤回影响后续访问与执行。

实现顺序见[路线图](roadmap.md)。身份、事务存储和可靠派发是建立真实多人服务的前置条件，不能把当前本地文件存储原型当成已经满足这些要求。
