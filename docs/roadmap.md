# 开发路线图

本文件管理验证与开发顺序，阶段含义与[产品规划 v0.2](product-plan.md)一致。当前可运行范围见[README](../README.md)，需求观察方法见[试点验证计划](validation-plan.md)。按通过条件推进，暂不承诺开发周数。

## 已完成的工程起步

- 独立科研数据核心与十项 Skills 加载包。
- 来源记录、内容检查、构建、类型检查、基础测试与演示。
- Harness 适配源码单独保留；公开 SDK 依赖问题与实际运行待验证。
- 统一 README、协作方式、任务与 PR 模板。

这些基础不代表下面的产品阶段已完成，也不能证明科研效果或市场需求。

## M0：选定真实需求与完成标准

先收集近期真实工作，填写试点卡：使用者、作者、原有做法、具体输入输出、采用标准、访问范围和下一次使用机会。建议从“资料与依据整理→材料草稿或修改”中选择一个具体场景，允许根据观察替换；不同时铺开论文、申请、实习生管理等全部领域。

通过依据：一个明确的实际交付物、可取得的样本、愿意参与的作者与非开发使用者，以及双方认可的结果检查方式。尚未观察到的困难标为假设，不写成已验证需求。

此时只进行会影响可行性的必要技术验证：确认所需材料和工具能接入、选定 Harness 版本能实际运行。技术限制应反馈到产品承诺，不以搭好通用框架代替选定任务。

## M1：完成一条最小平台过程

围绕 M0 的同一场景，实现产品规划 R1–R7：成员与项目、能力选择、后台任务、资料与成果检查、项目记忆、作者发布与反馈、数据导出和访问收回。使用者能够完成“选择→执行→检查→留存→下一次或他人继续”，作者能够根据一次真实反馈处理能力问题。

必要工程验收：

| 工作 | 通过依据 |
|---|---|
| Harness 接入 | 固定可安装版本，在真实环境验证工具和 Skills；替身测试不替代实际运行 |
| 成员与项目授权 | 不同成员、不同项目的页面、接口与工具遵守同一访问范围；撤回授权影响新任务和受影响的进行中任务 |
| 任务与执行关联 | 任务对应执行尝试、输入、输出和能力版本；待输入、取消、失败、中断均可追踪；限制与重试实际有效 |
| 资料与记忆 | 原文可核对；新会话能取回相关授权内容，区分候选、确认与已替代信息；内容可移除、成果可导出 |
| 后台与重启 | 关闭浏览器后任务继续受管理；重启后待执行任务可领取，运行中断有明确恢复或重跑办法，不重复已发生的外部操作 |
| 能力维护 | 发布验证范围与状态真实；新版不改变旧任务关联；停用后不接受新任务 |

个人长期偏好、更多资料格式、定时与周期任务、更丰富的检索和通知先列为 P1。若 M0 选定的任务本身依赖定时触发，则将最小定时能力纳入 P0，同时验证所有成员离线时仍可触发。与 v0.1 相比，这是有意收敛首版范围，不改变持续工作与知识留存的目标。

界面只呈现实际接通的能力和真实状态；没有合适能力或不能执行时清楚说明。

## M2：验证非作者的独立与重复使用

让未参与开发的成员实际使用，记录作者帮助、检查返工、成果采用、失败与放弃。等下一次同类需求发生，观察是否主动复用。至少跟踪一次真实反馈、作者修订及修订后再次使用。

通过依据是具体案例中独立完成、自然重复使用和可解释的净收益，包含成本与失败记录。暂时没有下一次任务时保留待观察状态；不以演示次数或每日登录代替证据。

## M3：验证其他课题组与外部作者

沿相似任务和合作关系接入其他小组，检验用户能否复用、外部作者能否按共同规则贡献，以及引入和维护成本。必须能说明哪些能力跨组通用、哪些只能定制，不能默认每扩张一个组织层级产品就成立。

个人付费、课题组付费和学校采购分别验证。公开市场、支付分成、全校接入和任意第三方代码安装，等相应证据出现后再规划。

所有阶段分别记录代码检查、科研结果和产品需求证据；每轮选择继续、收窄或替换场景，并更新规划。
