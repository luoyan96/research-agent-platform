# 阶段验收与证据

日期：2026-09-21。以下全部是**待执行**的验收要求，不代表已有功能。关口和分工见[开发索引](README.md)。

## 怎么判断通过

- 每条记录为“通过 / 失败 / 未验证”，附环境、代码提交、契约版本、操作、预期、实际结果及证据。阻塞属于未验证，写清原因。
- 前端预览、服务联调、真实模型与 Harness 执行分别记录；不能用一个截图或根 CI 通过替代其他证据。
- 同一阶段的前端、后端和联调项均通过才能宣布该关通过。部分可独立工作的内容可继续准备，但不能把未通过的关口改成完成。
- 所有自动验证用合成 A（发起 / 验收）、B（承接）、C（无关或竞争认领）的账号与资料。不同情形用不同任务，明确各自权限。浏览器使用独立登录会话。
- 先核对接口和数据库，再核对界面；验收者可以复现。证据中的令牌、凭据和真实研究内容不得提交 Git。
- 完成代码检查后不无理由重复全量测试；新代码、失败或新风险需要对应验证。每阶段最终报告说明新增应用是否纳入根检查。

## G1 · 人的协作

| 案例 | 操作 | 必须看到的结果 | 证据 |
| --- | --- | --- | --- |
| A1 草案与确认 | A 建方案、修改版本；尝试确认旧版本；确认新版本后重复同一请求 | 旧版本冲突；确认前没有有效分配；相同 key 重试只产生一组稳定任务；同 key 不同负载被拒绝 | API、事务记录、F1 界面 |
| A2 接受与拒绝 | A 分别邀请 B 承担两项任务；B 接受一项，拒绝另一项 | 接受前不记为已承诺；接受后有约定范围；拒绝项可重新安排，不擅自转给 C | 两会话、邀请与承诺记录 |
| A3 并发认领 | B/C 对一项均有认领资格的开放任务同时请求牵头名额 | 仅一人成功，另一人收到冲突；数据库无双牵头，前端显示实际结果 | 真实事务并发测试、刷新结果 |
| A4 交付与验收 | B 不披露私有工具提交文本版本；A 退回，B 重提，A 验收；重放提交 / 验收请求 | 交付先待验收，退回后需修改，验收指定版本后才完成；幂等请求不重复新增版本或决定 | 版本记录、双方页面 |
| A5 权限与持久化 | C 猜测受限任务 ID、伪造 actorId；A/B 刷新；服务重启后重新读取 | 越权失败且不泄露内容；主体由真实认证确定；已确认任务和承诺 / 交付仍在 | HTTP 响应、重启前后查询、会话记录 |

B1 需通过服务侧 A1–A5；F1 需通过对应真实服务交互；G1 在同一集成提交上复核完整链条。尚无真实模型时入口明确提供手工草案，不能据此宣称 AI 规划已通过。

## G5 · 小组真实试用

选一个近期真实任务，写清参与者、资料范围、交付要求和时间。至少一位非开发成员独立承接、交付；发起人能从总览找到卡点并完成验收。记录用户整理 / 催问 / 返工 / 维护投入，以及下一次需求是否愿意继续使用。保存去敏试点结论，不上传研究原文。

内部试用通过不代表市场验证、学校采购或所有智能体都已经可靠。
