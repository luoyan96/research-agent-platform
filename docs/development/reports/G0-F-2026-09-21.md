### 修复

删除所有手写 `mine` 布尔值。`projectTask` 从 Task 的 initiatorId / leadId / participantIds / reviewerId，以及同任务、kind=invitation、status=pending 的 Assignment.memberId 派生 scopeMemberIds；重复角色去重，空成员不纳入。`tasksInScope` 依据当前演示成员筛选，看板卡片、四列数量、需协调事项和入口最近任务共用这个结果。该逻辑只针对已可见的合成数据，不实现服务端鉴权；F1 仍必须消费服务授权后的 scope=mine 响应。

合成角色明确如下，A=洛、B=林、C=陈、D=王：

| 任务 | 发起 | 负责 | 验收 | 参与 | A 的个人范围 |
| --- | --- | --- | --- | --- | --- |
| patent | B | 未定 | C | 无 | 不包含 |
| intern | B | 未定 | B | 无 | 不包含 |
| proposal | A | A | A | B | 包含 |
| paper | C | C | C | 无 | 不包含 |
| data | D | D | A | 无 | 包含（验收人） |
| meeting | B | B | A | 无 | 包含（验收人） |

正常场景没有待回应邀请；待回应邀请的纳入和非待回应状态的排除由独立、经共享 Assignment Schema 校验的样例覆盖，不伪造真实邀请服务。

### 回归检查

`apps/web/tests/scope.spec.ts` 新增 15 项：每个正例只有一种与 A 的关系，分别验证发起、负责、参与、验收、待回应邀请；验证无关成员、无当前身份、其他任务/其他成员/其他分配类型、空对象、拒绝/撤回/取消/转交、已接受邀请、重复角色及关系移除。另直接重建验收问题的数据：当六项都由 A 发起/验收时必须返回六项，防止将三项固定数量当作正确性依据。
