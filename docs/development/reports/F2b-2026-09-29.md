## 已实现与操作路径

入口、草案、四列总览、人员和协作主线继续复用；无固定侧栏、无六套任务应用。首页及待办明确区分待回应变更、邀请与验收，总览增加本人待回应变更数量。

1. 手工方案 → 展开时间安排 → 填建议时间、明确确认的硬截止、检查节点及预计投入；未知留空。支持日期 + IANA 时区或带偏移的绝对时间。草案不能写入成员承诺，承诺在接受邀请/认领或必要成员接受变更后形成。前置草案项可多选，环由服务拒绝。
2. 任务详情 → “变化与异常”按需展开 → 报告受阻，记录原因、需要谁回应、恢复动作。依赖显示任务关系及要求的验收版本，影响显示受影响交付、复核状态和服务允许的来源；无权上游不猜测名称。依赖恢复后明确复核，再单独恢复任务。
3. “提议范围、时间或依赖变更” → 填范围、目标、验收、时间、依赖和原因 → 必要成员接受/拒绝。待接受提议与当前有效安排、已有承诺同时显示；拒绝或失败不应用。已结束提议折叠为历史，其比较栏明确是当前安排，不冒称重建历史基线。
4. “退出或转交” → 原成员说明原因/剩余范围/候选人 → 成功回执清理原详情。候选人仅获承接摘要，另行接受才形成承诺，不能沿用前任承诺日期。
5. 取消与撤权在相应任务展开，要求说明并明确确认；按钮依据服务 allowedActions，变更回应依据服务返回的必要回应名单/已有决定。附件撤回沿用服务返回的发起人撤权能力并由端点重新鉴权。前端不授予权限、不更改状态机。
6. 附件 → 选择文本/PDF/PNG（1 byte–10 MiB）→ 上传成功后重读 → 勾选到交付 → 提交新 revision。上传失败无可引用记录。每次下载是有认证的 no-store 二进制请求，临时 Blob URL 使用后立即撤销，不提供永久链接。撤回保留元数据、交付 ID 引用和历史，阻止内容下载。
7. 任务事件历史沿用同一快照，20 条分页；业务更新后旧快照明确失效并整组重取。

`src/schedule-editor.ts` 负责共享 Schedule 字段编辑；`src/coordination-view.ts` 组合任务内操作、比较与附件；`collaboration.ts` 继续复用现有会话/幂等、导航和协作组件；没有新 UI 框架或额外接口。

## 输入、重试和权限

同一失败请求保留不可变正文/key；新意图先明确放弃未决请求。新增协调输入保留原任务版本，刷新显示编辑基准与最新状态，明确重新确认后才基于新版本提交。成功操作只清理对应表单输入；其他未提交协调内容保持原版本基准。同账号会话失效保留输入及请求，显式退出或换账号整体清理。任务 403/404 同时清除该任务编辑基准、未提交输入及未决请求，后续授权重读不复现旧内容。两处本人任务入口仍清空旧 lab/status/page 筛选。

列表及任务详情在可见时每 15 秒检查快照（通常 15–30 秒发现失效），不会宣称实时通知。离线事件、失效/权限错误清理呈现；在途读取及下载中止，晚到 JSON/二进制不能重新填充。隐藏页不保证即时发现；返回后探测，下载始终即时服务鉴权。未提交内容仅留当前内存，不冒充服务端草案。已下载到设备的副本无法追回。
