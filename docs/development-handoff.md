# 第一版开发交接

日期：2026-09-21。用户已初步接受简洁入口、实验室看板和任务详情的视觉方向，允许按使用反馈再调整。下一阶段是实现；本次交接没有新增应用代码。

前后端分工使用[分阶段开发索引](development/README.md)：分别提供[前端指南](development/frontend.md)、[后端指南](development/backend.md)、[共享契约](development/contracts.md)、[阶段验收](development/acceptance.md)和[可复制启动 prompt](development/prompts.md)。多人开发优先使用这些按批次限定的指令；本文保留整体范围和顺序。

## 交付目标

让同一实验室的几位成员通过浏览器，真实完成一次“提出需求 → 确认协作方案 → 人和公共智能体分别承担 → 交付验收”的过程。浏览器离开后，任务与承诺仍存在；实验室看板展示同一套真实数据。

论文、科研项目、知识产权、实验与数据、学生培养、汇报事务是可扩展的任务类型，不是六套应用。用户无需先建项目或选择工作流。

## 当前代码边界

已有本地 Project / Artifact 存取、Skills 加载与十项方法资源。没有团队账号、平台数据库、任务服务、网页或执行服务。已有文件存储不适合直接成为多人事务数据库。

Harness 适配仍待干净安装和真实联调；[已记录的依赖问题](../integrations/deepseek-harness/README.md)是当时的检查结果，开发时必须重新验证。不能因根目录 CI 通过就声称 Harness 已接通。不要复制旧探索界面的导航与项目工作流。

## 第一版范围

| 必须建立 | 最小实现 |
| --- | --- |
| 身份与访问范围 | 小组成员身份、任务可见范围、个人能力所有者权限；所有服务端入口检查权限 |
| 任务与方案 | 自然语言需求、结构化草案、版本修改、确认；目标、交付与验收要求允许逐步补齐 |
| 分配与承诺 | 本人承担、邀请与接受/拒绝、开放认领、公共智能体执行；防重复确认与并发认领 |
| 实际进度 | 依赖、开始、受阻、截止建议与承诺、变更、取消、提交、退回修改、验收 |
| 看板与人员 | 实验室 / 我参与的两种范围；阶段、卡点、下一节点；公开承诺与成员自报可用时间 |
| 真实 AI | 基于可见信息生成协作建议；至少一种公共能力经 Harness 实际产生可检查的交付物 |
| 持久运行 | 任务、事件与运行记录落库；任务派发去重；关闭浏览器不停止服务端管理；重启明确恢复或标记中断 |
| 资料与积累 | 附件、交付版本、验收反馈与已确认结论可复用；保留权限、来源与用途范围 |
| 能力边界 | 个人可用私有或平台外方法交付；公共能力与个人能力分开；最低限度的登记、版本、停用与明确共享 |

先选择“基于用户提供材料整理清单”等可核对的小能力验证公共执行，实际能力由工具和评测决定。不要把存在一个 Skill 文本当成已经能够完成检索、事实核查或科研写作。

“描述需求 → 生成能力草案 → 样例试跑”可在主流程通过后补齐。自动改写并发布能力、跨学校生态、支付、复杂周期调度和完整人事系统留待后续。九张图的落地可以分批，未完成部分如实标记，不能显示假成功。

## 开发顺序与交付物

| 批次 | 开发内容 | 可检查的结果 |
| --- | --- | --- |
| D0：接入与契约 | 核查基础包及 Harness 可用版本；确定服务器、事务数据库与文件存储方案；定义共享类型、接口和状态转换 | 一个最小真实 Harness 调用记录或明确阻塞证据；固定版本；接口约定与迁移计划。Harness 受阻不阻止独立的人类协作功能开发 |
| D1：真实任务服务 | 成员身份、权限、任务/方案/承诺/依赖/交付/验收持久化，含去重、并发与取消规则 | 两个成员通过真实 API 完成邀请或认领、交付与验收；权限和争用测试通过，重启后数据仍在 |
| D2：浏览器协作 | 对话入口、方案确认、认领、聚焦待办、验收、实验室总览与任务详情接到同一服务 | 两个独立登录会话完成同一任务；界面跟随真实状态变化，有加载、空、失败、不可访问状态 |
| D3：AI 与后台执行 | 真实模型生成建议，接通已验证的公共能力与持久派发、用量限制、取消和失败处理 | 关闭浏览器后运行仍受管理；实际产物可验收；失败或中断不会变成“已完成” |
| D4：能力与任务记忆 | 个人能力选用、最小草案与样例验证、明确共享、版本维护、按权限复用已确认结论 | 私有方法不泄露；同一用户可继续使用自己的能力；公共更新不吸收未经授权的私有材料 |
| D5：组内试用 | 用真实任务走一遍、记录问题并修正 | 非开发成员可独立承接；完成试点记录，明确剩余限制 |

前后端可以分工，但先共享 D0 的类型、状态与接口契约。分别使用任务分支并指定集成人；同一接口变更同时更新契约和相应调用方。没有必要让多个代码 AI 同时重写整个仓库。

D0 的技术选型是实现决定，应核实依赖和兼容性后落文档；本交接不把未经验证的框架版本当成既定事实。原有基础包与适配边界保留，新增应用目录由实现方案明确。

## 看板不另建一套状态

业务状态以任务分配文档为准。四列是面向用户的聚合：

- 待安排：待安排、待承接、尚未开始的任务；卡片保留具体状态。
- 进行中：进行中、受阻、需修改；显示卡点和实际下一步。
- 待验收：已经提交明确版本、尚未验收。
- 已完成：已经验收；已取消单独记录和查看，不混成完成。

复合任务与可分配的子任务分别建模：父任务有自己的目标和验收；不能因为部分子任务完成就自动完成父任务。任务详情的“已验收 1 / 5 项”仅是约定交付项数量，不表示已完成 20% 工作量。依赖图不得有环。

人员负荷不由任务数量或在线时长推断。可用时间由本人提供并标记适用周期与更新时间，缺失时显示未知；成员私有任务不通过统计、提醒、搜索、导出或推荐理由泄露。

## 第一版必须通过的验收

使用合成资料自动测试，真实小组试用另行记录。所有测试都要核对最终存储与接口状态，不能只看页面文字。

1. 用户一句话生成可修改方案；未确认不派发，重复确认不重复创建任务；真实模型未配置时明确显示不可用。
2. A 邀请 B，B 可拒绝；两人同时认领同一牵头任务仅一人成功；已接受的承诺不能被新建议静默覆盖。
3. B 使用未登记的个人方法提交结果也可验收；A、无关成员和公共维护者无法取得 B 的私有能力或日志。
4. 提交成果后进入待验收；退回修改后不能显示已完成；智能体执行结束不代替人工验收。
5. 看板、人员当前承诺和任务详情使用相同权威数据；刷新、换登录会话和重启后状态一致；无权限数据在聚合中也不可见。
6. 依赖未满足不派发；取消、撤权和重启的处理有测试，外部动作不因重试重复产生。
7. 至少一个真实公共能力通过 Harness 执行并保存可检查成果；依赖或凭据不可用时保留失败证据，不用模拟结果替代验收。
8. 后续任务仅复用有权读取的结论；默认不将个人方法、反馈或样例发布到公共库。

这是便于开发的摘要，不删除 [原有十个验收场景](task-allocation.md)。共享代码或打包 Skills 变更执行 `pnpm run ci`，并增加对应集成与浏览器验证；默认 CI 不覆盖 Harness 和真实模型效果。

## 可直接交给代码 AI 的启动指令

以下适用于一个 AI 负责整体起步；前后端分开交接时，改用[各自的第一步 prompt](development/prompts.md)。

> 在 research-agent-platform 仓库开始第一版实现。先阅读 AGENTS.md、docs/development-handoff.md、docs/design/README.md 和 docs/task-allocation.md，查看相关 PNG。沿用已确认的简洁界面和实验室任务看板，复用现有基础包，按 D0 → D1 开始，完成一个可审查的小批次并报告结果。
>
> 核查并固定 Harness 的可用版本，明确实际接入状态；先统一数据模型、接口和状态，再实现成员权限与真实持久化任务协作。不要把本地 ArtifactStore 直接当作多人数据库，不要用私有能力做共同匹配，也不要用前端写死的数据或模型文本冒充执行和验收状态。
>
> 用独立任务分支，保留现有改动；完成适当测试与 pnpm run ci，给出运行说明、验证结果与剩余限制。真实模型调用若缺少必要凭据，明确指出缺项并继续不依赖凭据的开发；不打印密钥，不自行部署或发布。
