# 组内试点验证计划

对应[产品规划 v0.2](product-plan.md)。本文件是待执行的记录方法，没有已完成的访谈、实验结果或市场数据。涉及真实科研内容的记录存放在受控项目空间；本公开仓库仅保留空白模板、可公开样例与汇总决定。

## 1. 先找实际工作，再决定首发能力

建议请首批参与者各带一项最近完成或近期必须完成的任务，展示当时的输入、交付物、工具和困难。优先问“上一次具体怎么做”，不要只问“你是否想要一个智能体平台”。

| 要记录的内容 | 需要的事实 |
|---|---|
| 工作与发生时机 | 为谁做什么、何时交付、多久出现一次、下一次预计何时发生 |
| 原有方法 | 使用哪些工具、谁参与、在哪些步骤等待或求助 |
| 输入与使用范围 | 材料能否取得与读取、哪些资料可用于试点、哪些人有权看到 |
| 完成标准 | 什么具体内容必须正确、谁检查、什么情况下无法采用 |
| 时间与成本 | 准备、实际操作、检查、返工和交接；没有记录的旧任务注明为回忆估算 |
| 复用机会 | 下一次可以沿用哪些背景、是否有同伴做相似工作、谁能把方法提供给别人 |

对候选任务逐项判断：近期确实会发生，输入可用，结果能检查，原有困难明确，存在非作者复用机会。优先选择满足这些条件的一个具体场景；不能只以模型容易生成好看文本为依据。

产品规划中的“资料与依据整理→材料草稿或修改”是建议候选。如果样本不支持它，记录替换原因并更新产品规划和路线图。

## 3. 按真实使用机会观察

**A. 作者先验证能交付。** 在选定任务边界内检查输入、运行、来源和结果，保留失败与不适用样例。作者自己演示成功只是发布准备，不能计为非作者独立使用成功。

**B. 非作者独立尝试。** 提供正常使用说明，让参与者自己选择能力并处理任务。观察者可以在卡住时帮助，但必须记录帮助内容和时间；这一条不能继续标为独立完成。结果由约定的检查人按试点卡判断。

**C. 换会话与换成员。** 在实际后续任务中检查已有资料、成果和确认记忆是否起作用。不同项目验证访问范围，不能把共享全部材料当作成功复用。后台任务和异常恢复由工程验收配合检查。

**D. 等待下一次自然需求。** 记录是否再次使用、改用其他方式或放弃，以及原因。还没有第二次任务时标为“尚无观察机会”，不提前宣布留存成功或失败。

**E. 让反馈回到作者。** 至少观察一次真实问题如何形成修订，及修订后他人是否继续使用；同时记录作者维护与支持投入。以后引入外部作者时，要另行观察其加入和持续维护的动机。

建议试点覆盖至少两位能力作者、两位使用者，角色可以重叠，其中至少一位使用者未参与开发。两个有不同访问范围的项目用于检查共享边界。这是小样本观察设计建议，不是已经到位的人员，也不是市场证据。

```text

如何找到并选择能力，是否选错或找不到：
是否首次使用 / 是否存在过前一次同类需求：
技术执行：完成 / 失败 / 取消 / 中断 / 尚在等待输入
成果判断：待检查 / 已采用 / 需修改 / 未采用
采用标准的检查结果、主要错误与来源核对情况：
是否获得作者或维护者帮助，具体帮助与耗时：
人工投入：准备 / 操作 / 检查 / 返工 / 交接
任务等待时间、模型与其他服务成本：
作者支持与维护投入（共享维护成本另外累计）：
是否取用了旧成果或记忆，正确、缺失或过期情况：
与原有做法相比的改善与新增负担：
不采用、取消、放弃或改用其他工具的原因：
反馈处理方式、是否进入能力修订：
下一次实际需求时是否复用及原因（出现后补记）：
```

技术完成与成果采用分别统计。分母包括真实启动的失败、放弃和未采用任务；尚未结束的任务单独列明。发现能力前就因找不到、看不懂而退出的情况也单独记录，避免漏掉入口问题。

人工收益比较包含准备、操作、检查、返工和交接，不只比较模型生成速度。作者支持、平台维护与能力开发分别记录；一次性建设投入和每次运行投入分开报告，不能隐藏其中一项。等待时间与费用单独呈现，若需要折算为钱，先说明采用的时间成本假设。

尽量比较同类、相近复杂度的真实任务。同一个人重复做同一任务会有熟悉效应，不能将第二次更快全部归因于平台。旧任务只能回忆估算时标明证据较弱，不宣称已经完成严格对照。

## 5. 什么时候继续，什么时候调整

每轮真实任务结束后，按以下问题作出记录，而不以仓库提交数、能力条目数或演示效果决定扩张。

| 观察结果 | 下一步 |
|---|---|
| 非作者能独立获得可采用结果，下一次需求主动回来，支持投入可承受 | 继续完善同类任务，并验证其他成员和项目 |
| 能运行但成果无法采用，或检查返工抵消收益 | 收窄任务边界、改进质量，再验证；暂缓增加能力数量 |
| 作者不在就无法使用，或每次都需要大幅定制 | 修改输入要求、说明和配置，重新判断哪些部分能够通用 |
| 主要价值来自个人上下文，跨成员能力复用未出现 | 保留有价值的连续工作能力，重新评估平台供给侧投入；暂不宣称双边平台已成立 |
| 新成员有需求但目录没有适用能力 | 记录缺口并检查是否高频、可交付，再决定招募作者或新增能力 |
| 需要逐组重建产品，或外部作者支持成本过高 | 停止扩大接入规模，先解决复用边界与维护方式 |
| 出现越权读取或严重的依据失真 | 暂停受影响的能力或数据范围，修正并复核后恢复 |

以上是试点判断规则，不是已达到的指标。进入 M3 前，应有可追溯的非作者采用、自然重复使用和反馈改进案例，并解释仍然存在的失败。具体成本上限由团队在试点卡中确定；当前没有据此设定收费方案、用户规模或收入预测。

## 6. 留下什么决定

每轮形成一份简短记录：观察到什么、哪些假设获得支持或仍未成立、继续哪项任务、暂停什么、谁负责下一次改进。可公开的结论可进入 Git；具体研究资料、成员对话和可识别的个人使用记录不进入公开仓库。
